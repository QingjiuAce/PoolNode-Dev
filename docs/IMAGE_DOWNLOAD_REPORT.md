## 1. TL;DR

- **早高峰单流下载可达 27 Mbps（冷）/ 136 Mbps（连接复用稳态）**，线路本身档位不低；
- **晚高峰回程崩塌至 0.4–0.6 Mbps（单流）**，21:04 复测无恢复——瓶颈为**回程 PCCW BGP 的
  per-flow 晚高峰整形**（并发剂量实验 1→16 流线性扩展已实证，非聚合令牌桶）；
- **去程三网直连不受影响**：上传方向晚高峰 45.9 Mbps，与早间持平甚至略升；
- 服务端两台机器（Pool 300M 口 / CN2 盒子 10M 口）端口本身均不堵（同时刻 CF 上行
  189 Mbps / 港内拉满 10M 口），**瓶颈 100% 在"国际回程 → 大陆移动"段**；
- **已验证的解法排序**：客户端分段并发（免费、零服务端改动，16 流 ≈ 6.35 Mbps）>
  CN2 路线（2.3–2.9 Mbps）> EdgeOne 免费版（待实测）> CF 免费版（**已否决**）；
- jsDelivr 全变体（**已否决**）、Gcore 免费版（待实测）。

#### 32/64 流探针：线性至 64 流，无悬崖（勘误 2026-11-23）

**勘误**：本节初版（2026-11-22 深夜回填）把 curl 批量的**单流均摊**
（`f["size"]×8÷墙钟`）误读为聚合吞吐，得出"32 流骤降至 0.34 Mbps、13 倍下跌、
悬崖式反 flood 响应"的错误结论。实际 curl 批量是 w 条**完整并行下载**，
总字节 = w × 5,403,720 B；`bench_matrix.py` 已修正为 `w × f["size"] × 8 ÷ 1e6 ÷ 墙钟`。
原始记录（results.jsonl 的 wall/size/连接数）未变，以下为直接重算：

| 流数 | 总字节 | 中位墙钟 | **聚合吞吐** | 单流均摊 | 范围（聚合）|
| --- | --- | --- | --- | --- | --- |
| 32 | 32 × 5.4MB = 172.8MB | 127.66s | **10.84** | 0.34 | 10.58–11.83 |
| 64 | 64 × 5.4MB = 345.6MB | 124.77s | **22.17** | 0.35 | 21.16–22.65 |

墙钟自洽：32×5.4MB ÷ 10.84 Mbps ≈ 127.7 s ✓；64×5.4MB ÷ 22.17 ≈ 124.9 s ✓。
**32→64 流严格 ×2.05，近线性，无拐点**。单流均摊自 1 流 0.50 缓降至 64 流 0.35
（-30%，存在轻微共享分量），但聚合持续爬升。初版"悬崖式反 flood 响应"结论**撤回**，
"A1 的 16 段为安全上限不得提升"一并作废；§7 开放问题 1（饱和拐点）**关闭**。
完整剂量-响应表与混杂变量声明见
[NOTE.md](../reports/benchmarks/v04-beta-peak/NOTE.md)。

#### 超额并发后恢复测试

32/64 流大批量（各 5 轮）结束后立即复测：**16 流聚合 = 5.20 Mbps**（不低于基准
中位 4.54）、单流 = 0.4 Mbps 不变——**高并发批次无持续惩罚**，路径立即恢复。

#### 50 轮完整性核查

- 实际 TCP 连接数与预期**逐轮精确一致**（1/5/9/17/32/64；`Connection: close`
  每 GET 一连接，服务器访问日志逐行核对）；
- **重试 0 次、回退 0 次**（全部 50 轮）、**SHA256 50/50 通过**；
- 1.7MB 组复现了此前实测（w4 ≈1.27 / w16 ≈3.40 Mbps，同量级）；
- 2.01MiB（阈值边界）与 5.40MB（默认 16 流档）行为一致，per-flow 基线与文件大小无关。

#### 事故记录

初次 smoke 组（1.7MB ×10 轮）失败：服务器侧白名单 `/etc/pool-poc/assets.yaml`
的 smoke 条目**缺少 `size_bytes` 字段**（该字段为 v0.4-beta 新增，服务器部署早于
此字段），客户端按设计拒绝无登记字节数的下载。已在服务器白名单补录
`size_bytes: 1778514` 后重新验证通过（中位 w4 1.27 / w16 3.40 Mbps，见上表）。
教训：**服务器白名单是客户端依赖的契约面，新增字段需同步补录**。

#### 客户端测试 vs 传输层探针的区分

- **40 轮客户端测试**：走完整 `pool.fetch` 语义（白名单授权、强 ETag/If-Range、
  206 拼接、SHA 校验、原子发布）——是交付能力的直接证据；
- **10 轮 32/64 传输层探针**：仅 curl 裸并发 GET（`-o /dev/null` 级验证）——用于
  探测并发线性边界：**64 流仍近线性、无反 flood 悬崖**（见上方勘误）。但该数据
  为多文件整传，**不构成单文件分片并发的证据**；单文件更高分片数是否采用，交由
  v0.5 动态调度任务以单文件配对实验决定。

## 4. 根因分析

1. **方向不对称**：去程三网直连（请求/上传快）vs 回程 PCCW BGP（下载晚高峰被整形）。
   用户感知的"下载慢"100% 落在回程国际段。
2. **整形方式为 per-flow**：并发线性可绕，**至 64 流无拐点**（32 流聚合 10.84、
   64 流 22.17 Mbps，32→64 严格 ×2.05；§3.7 勘误）。
3. **两台服务器端口均健康**（同时刻 CF 上行 189 Mbps / 港内拉满 10M 口）——排除了
   服务器自身瓶颈，也排除了"整站被限"。
4. **晚高峰劣化深度大且持续**（20:30 → 21:04 无恢复），对 5.67MB 级原图：
   晚高峰单流下载 ≈ **2–10 分钟/张**，完全不可用；预览图（20–80KB）≈ 1–2 秒，可用。

  生产配置与数据；第三方路线测试仅读取公开文件（dl.bszx.site 自有资产 / GitHub 公开

  详见 §3.7）

  [OPTIMIZATION_ROADMAP](OPTIMIZATION_ROADMAP.md)）
